# ExportDrive 团队协同开发规范

## 问题背景

导出驱动器使用多对话（worktree）开发模式，每个对话有独立的工作区。**部署时只会部署当前工作区的代码**，不会自动合并其他对话的改动。如果多人同时开发、先后部署，后部署的会覆盖先部署的。

## 协同工作流（三步走）

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  开发前同步   │ ──▶ │  独立开发     │ ──▶ │  部署前检查   │
│  git pull    │     │  写代码       │     │  pre-deploy  │
└──────────────┘     └──────────────┘     └──────────────┘
```

### 第一步：开发前同步

每次开始写代码前，确保工作区代码是最新的：

```bash
git pull origin main
```

### 第二步：独立开发

在自己的工作区正常编写代码，修改、测试、验证。

### 第三步：部署前检查（关键！）

**部署前必须执行**，确保不会覆盖别人的改动：

```bash
bash scripts/pre-deploy-check.sh
```

这个脚本会：
1. 检查是否有未提交的本地改动
2. 拉取远程 main 分支最新代码
3. 如果有冲突，提示手动解决
4. 确认安全后才允许部署

## 分支策略

| 分支 | 用途 | 说明 |
|------|------|------|
| `main` | 稳定分支 | 始终与已部署版本一致 |
| `feature/xxx` | 功能分支 | 大功能可以开分支，完成后合并回 main |

日常小改动直接在 main 上开发，大功能建议开 feature 分支。

## 冲突处理

如果部署前检查发现冲突：

1. 脚本会列出冲突文件
2. 手动解决冲突（保留谁的改动）
3. `git add` 标记已解决
4. `git commit` 提交合并
5. 再次运行 `bash scripts/pre-deploy-check.sh` 确认
6. 确认无误后部署

## 常见场景

### 场景一：我先部署，别人后部署

```
时间线：
  09:00  主仓代码 V1
  10:00  你改完 → 执行 pre-deploy-check → 无冲突 → 部署 ✅ (V1+你的改动)
  11:00  别人改完 → 直接部署 ❌ (覆盖了你的改动)

正确做法：
  11:00  别人改完 → 执行 pre-deploy-check → 检测到远程有新提交
         → 自动合并你的改动 → 解决冲突 → 部署 ✅ (V1+你的改动+别人的改动)
```

### 场景二：多人同时开发不同模块

```
  你改 /documents 页面
  别人改 /shipping 页面

  谁先部署谁先上，后部署的人执行 pre-deploy-check 自动合并即可。
  因为改的是不同文件，通常不会有冲突。
```

### 场景三：多人改同一个文件

```
  你和别人都改了 src/app/page.tsx

  后部署的人执行 pre-deploy-check 时会提示冲突。
  需要手动选择保留哪些改动，解决后再部署。
```

## 最佳实践

- **小步快跑**：改完一个小功能就部署，不要攒一大堆
- **先同步再动手**：每次开始写代码前先 `git pull`
- **部署前必检查**：养成 `bash scripts/pre-deploy-check.sh` 的习惯
- **沟通先行**：改同一个模块前，先和团队沟通
