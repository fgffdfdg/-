# 部署、发行保留与回滚规范

每次发布、重试、清理、回滚及 AI 临时命令、手工步骤、CI 都必须先读取本规范。用户当前明确指示优先；本次仅改 MD，不表示脚本、平台或生产已经生效。

## 项目边界

本仓库为 Coze／Next.js 的 ExportDrive；实际构建和启动见 `package.json`、`scripts/build.sh`、`scripts/start.sh`。云数据库和对象存储独立，浏览器 localStorage／IndexedDB 另有仅本设备资料。发布前仍执行 `scripts/pre-deploy-check.sh`，但其同步检查不等于备份、生产部署或恢复验证。当前无统一保留管理入口，具体托管环境和数据库／文件恢复能力待逐次核实。

## 保留对象

| 对象 | 规则 |
| --- | --- |
| 程序／安装包 | 发布后常态保留当前版＋上一已验证稳定版，部署中可临时候选版；失败尝试不能替换稳定版。保护它们引用的依赖，先解除并验证旧目录引用再清理。 |
| 更早代码 | GitHub 完整 SHA、锁文件、运行时、产物摘要和配置版本引用用于重建；源码或压缩包不是数据恢复点。原始归档保留，不套用旧程序清理。 |
| 持久业务资料 | 数据库、附件和密钥独立保存，配置只记安全引用；迁移前新建一致性备份，日常备份另行。本地目标最近 2～3 份成功备份＋仍必要的迁移保护点；不能以部署规则删除业务原件或用户自行保存的档案。 |
| 异地副本 | 目标每日 7 份、每周 4 份，在服务器之外存储并校验上传、实际恢复；未配置／未验证时记为待落实，不能用同机副本冒充。 |
| 日志／缓存 | 轮转、限额，不反复打包历史备份或全部开发依赖。可运行版依赖不当缓存删除，业务备份不当部署缓存。 |

## 空间与平台

约 100 GiB 自管共享主机，以每台服务器旧发布目录＋本地历史备份合计 **15 GiB** 为起始预算，由主机负责人登记各项目用量和分配，不能每项目各 15 GiB；香港、广州等不同主机分别统计，可按实际体量调整并记录。当前运行版和在线业务数据不计历史预算，但计全盘占用。预估构建、候选、新备份、验证暂存和安全余量，避免重叠目录重复计数。

自管磁盘达到 80% 提醒；达到 90% 或预计峰值空间不足则暂停本轮新部署，以先触发者为准。最低保护副本超预算先转移至已验证存储或扩容，不强删保护点；此规则不取消必要的日常／应急备份。平台托管按实际产物、数据库、对象存储配额和正式恢复能力检查，不强套本地 15 GiB；桌面／归档不凭空套用云服务器配额。

## 每次执行

1. 固定完整 SHA／不可变安装包，核对目标环境、有效配置、迁移、实际产物和运行状态；采用部署锁或平台互斥，中断先核实恢复，禁止并发部署／清理／恢复。
2. 相同 SHA 仅在配置、schema、产物及适用的进程／关键健康均匹配时跳过重复构建、备份和重启；真正迁移前仍需新数据恢复点。未发布归档没有运行健康可冒认。
3. 输出用量、保留对象与清理预览；仅处理归属和状态明确的登记对象。未知 legacy 先核实再纳管，不按日期、名称或通配符直接删。
4. 保护当前版、上一稳定版、候选／活动任务、必要迁移点、故障现场及全部依赖。独立准备候选；有持久数据时用数据库认可的一致性方式备份，SQLite 用 backup API 或停止全部写入，PostgreSQL／云库用其适用备份能力，数据库与附件对应关系一并验证。
5. 先写临时备份并校验完整性／摘要／完成标记，禁止递归包含历史备份；切换后核对真实版本、登录、关键业务和附件。新版本健康及恢复链确认后再淘汰旧恢复点；服务恢复确认后才能清理不参与恢复链的失败暂存。
6. 缺少自动化时先补齐脚本，或采取同等安全、可审计并有预览的受控步骤；不能绕过条件继续无限备份。清理／日志失败不得阻断必要回滚，无法确认恢复时保留现场停止新一轮。

## 回滚与记录

- 程序／安装包回退需与当前数据兼容，只切回上一稳定程序及对应配置，保留最新业务资料，不自动回灌数据库。破坏性迁移先设计兼容或停写恢复路径及备份后新增数据的保留／合并，不能用 `git reset` 代替数据恢复。
- 有持久业务数据的项目，每月至少一次、重要迁移后追加隔离恢复演练，核对完整性、关键记录、登录、启动和附件；需要恢复时先停相关写入，在新目录／隔离环境验证并保留原数据。归档仅验证来源与文件完整性，不虚称业务恢复已通过。
- 记录目标／当前／上一稳定版本、运行时及锁文件、配置安全引用、迁移、备份路径／大小／摘要／验证结果、用量和清理预览、功能检查、对应回滚步骤及缺口；不记录明文凭据。包存在或上传成功不等于恢复已验证。
